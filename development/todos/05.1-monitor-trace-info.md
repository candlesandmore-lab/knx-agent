# ETS 6 Professional monitor trace export notes

Date: 2026-10-24

## Summary

Publicly available information confirms that ETS 6 Professional Bus Monitor and Group Monitor recordings can be exported as XML or CSV, but no public real-world ETS 6 monitor export fixture or formal XML schema was found.

The XML export is the better first ingestion target because KNX documents that it contains the raw cEMI frame as HexBinary. CSV is described as a human/Excel-oriented export and is likely less stable as a machine interface.

A real sanitized ETS 6 monitor export sample is still required before implementing exact XML/CSV parsing rules.

## Official KNX documentation found

### Telegram recording options

Source: <https://support.knx.org/hc/en-us/articles/360019034599-Telegram-recording-options>

Relevant findings:

- Recorded telegrams can be saved via the `Export` button in the Bus/Group Monitor toolbar.
- ETS prompts to save either all telegrams or selected telegrams.
- Export formats are XML and CSV.
- XML export allows editing stored telegrams with an XML editor.
- CSV export is intended for direct human reading or tools that do not understand KNX, such as Excel.
- KNX describes XML export as “more-or-less ETS internal”.
- The XML data is not encrypted; it contains the raw cEMI frame as HexBinary.
- ETS can reopen monitor recordings with extensions `*.xml`, `*.trx` from ETS3, and `*.hlg` from ETS2.
- Replay of recorded telegrams is available from Group Monitor.

### Bus Monitor, Group Monitor and ETS Bus Activity Monitor

Source: <https://support.knx.org/hc/en-us/articles/360018712880-Bus-Monitor-Group-Monitor-and-ETS-Bus-Activity-Monitor>

Relevant findings:

- Bus Monitor records and analyses all runtime bus telegrams.
- Bus Monitor needs exclusive bus access while recording.
- Group Monitor records/analyzes group telegrams and can read/send group address values.
- Group Monitor does not require exclusive bus access.
- Both monitors display telegrams in tabular form with configurable columns.
- Export/import controls exist in the monitor menu bar.

Documented monitor table columns:

- `#`: telegram counter
- `Time`: telegram recording time, using the configured monitor time format
- `Service`: bus service type, such as sent to bus or received from bus, plus trace start/stop
- `Flags`: control information, including standard frame or LTE-HEE frame
- `Prio`: KNX telegram priority
- `Source Address`: individual address of sender
- `Source Name`: sender name from ETS project data
- `Source Description`: source description
- `Destination Address`: individual address or group address
- `Destination Name`: destination name
- `Destination Description`: destination description
- `Building Function`: building function name
- `Building Part`: building part name
- `Hop Count`: routing counter / hop count
- `Type`: KNX telegram APCI service decoding
- `DPT`: datapoint type
- `Info`: additional telegram data, communication start/end, decoded value according to DPT
- `Medium info`: media-specific information for PL/RF
- `Security`: KNX IP Secure / KNX Data Secure information

Documented selected-telegram sidebar properties:

- `Acknowledge`: acknowledged / not acknowledged
- `APCI`: application layer control information
- `ConfirmFlag`: true/false
- `DataPointType`: datapoint type name if project is open and assigned
- `DecodedDpValue`: decoded datapoint value, such as On, Off, Open, Close
- `Destination`: individual address or group address
- `DestinationName`: group address name, or `-` if undefined
- `Building Function`: linked function name
- `Building Part`: linked building part name
- `FrameFormat`: Standard / Extended
- `LocalizedType`: KNX telegram APCI service decoding, such as Write or Read
- `MediumInfoRF`: RF domain address
- `MessageCode`: service and layer type
- `Priority`: Low, High, Alarm, System
- `RawData`: raw KNX bus telegram in cEMI format, consisting of service code and service data
- `RawDpValue`: raw datapoint value
- `RepeatedFlag`: true/false
- `RoutingCounter`: routing counter value
- `Service`: from/to bus
- `Source`: sender individual address
- `SourceName`: device name, or `-` if undefined
- `SystemBroadcastFlag`: true/false
- `TPCI`: transport layer control information

Important caveat from KNX: `RawData` is cEMI service code/service data and “does not correspond to the telegram on the bus in every detail”.

### Decoding telegrams

Source: <https://support.knx.org/hc/en-us/articles/360018986080-Decoding-telegrams>

Relevant findings:

ETS monitor decoding can be automatic or manual.

With project context, ETS chooses the datapoint type in this precedence order:

1. Datapoint type manually selected in the monitor for this telegram.
2. Datapoint type assigned to the group address.
3. Datapoint type assigned to any group object where that group object is the sending group object.
4. Default datapoint type from KNX master data for the associated group object size.

If more than one sending group object matches, KNX states there is no specific rule; ETS picks one randomly.

Without project reference, or if the group address is not used in the project, ETS may only perform basic bit-length decoding when the length can be determined from the bus telegram.

Manual decoding applies only to the selected telegram and is not applied to later telegrams with the same group address.

## Expected CSV shape

The CSV export likely mirrors the visible monitor table columns, because KNX says CSV is intended for humans and Excel-like tools.

Illustrative shape only, not a verified ETS export:

~~~csv
#,Time,Service,Flags,Prio,Source Address,Source Name,Source Description,Destination Address,Destination Name,Destination Description,Building Function,Building Part,Hop Count,Type,DPT,Info,Medium info,Security
1,2026-10-24 10:15:31.123,received,E,Low,1.1.10,Switch actuator,-,0/0/1,Living room light,-,-,-,6,GroupValueWrite,1.001,On,,
~~~

Exact delimiter, quoting, locale-dependent time format, column names, and whether raw cEMI appears in CSV remain unknown until a real ETS 6 CSV export is available.

## Expected XML content

The XML export is documented as ETS-internal and not publicly specified. It should contain the raw cEMI frame as HexBinary.

Illustrative shape only, not a verified ETS schema:

~~~xml
<Telegrams>
  <Telegram>
    <Time>2026-10-24T10:15:31.123</Time>
    <Service>received</Service>
    <Source>1.1.10</Source>
    <Destination>0/0/1</Destination>
    <RawData>...</RawData>
  </Telegram>
</Telegrams>
~~~

Exact root element, namespaces, timestamp representation, telegram element names, metadata fields, and HexBinary placement remain unknown until a real ETS 6 XML export is available.

## Implications for Todo 05

Recommended implementation strategy once a sanitized sample exists:

- Prefer XML as the first supported input format.
- Treat the raw cEMI HexBinary as authoritative for telegram decoding.
- Parse display/decode fields such as `DPT`, `Info`, `DecodedDpValue`, source/destination names, and descriptions as optional ETS-provided hints.
- Resolve source and destination addresses against the imported `.knxproj` project graph.
- Resolve DPTs from the project graph rather than trusting ETS display columns alone.
- Preserve ETS-provided decoded fields in provenance where available.
- Keep trace observations separate from project facts and accepted scenario state.
- Design CSV support as a secondary adapter unless the real CSV export includes the raw cEMI frame.
