# Todo 17: Module-instance support in the .knxproj import
Source: gap found after story 04 (user observation 2026-10-24 while checking the demo session): component `P-051B-0_DI-37` of the sample has 12 communication objects and 14 parameters that stay unresolved (26 import warnings `COMOBJECT_DEFINITION_UNRESOLVED` / `PARAMETER_DEFINITION_UNRESOLVED`), and the component is typed `UNTYPED`. Story 04 deliberately did not model `ModuleInstance`/`ModuleDef` (docs/implementation/003, 'Project import and project graph (story 04)'); no earlier todo covered it.
Goal: resolve module instances in the ETS 6 project import so that modular devices get complete communication objects and parameters:
- Parse the `ModuleDef` elements of the application program XML (arguments, numeric arguments, the communication objects, parameters and references inside the module definition) with streaming, as the program files can be 50 MB.
- Apply the `ModuleInstance` elements of the component in `0.xml` (module reference, `RepeatIndex`, argument values) to map the composite ids such as `MD-2_M-1_MI-1_O-2-1_R-1` and `..._P-1_R-1` onto their definitions: names, flags, datapoint types, defaults and values, with provenance.
- Fill the project graph: the 12 objects and 14 parameters of the sample component get names, flags and datapoint types; the 26 warnings for that component disappear; component typing (CT rules) sees the objects; direction labels in `trace_group_flow` become defined instead of `UNDETERMINED` where the flags allow.
- Everything needed is inside the `.knxproj` (the application program XML in the manufacturer catalog); no external KNX documentation is needed (vendor documentation for the meaning of a device is todo 09).
- Unsupported or unresolvable module constructs keep producing warnings (no silent guessing); update the warning descriptions and the golden counts (`tests/fixtures/sample_project_counts.yaml`: warning_total, warning_counts, component_type_counts, unresolved flags).
Open points for the architect (study the sample first): exact argument substitution and numbering rules of `ModuleDef`, nested modules, repeated modules (`RepeatIndex`), how xknxproject (dev cross-check only, GPL-2.0, no code copied) represents the same component for a comparison.
Validation: data-driven YAML fixtures, a synthetic `.knxproj` with a module definition and two instances (builder in tests/knxproj_builder.py), golden structure checks on the sample (skip when absent), SDK/CLI/MCP unchanged signatures, `describe-component` FULL and `trace-group-flow` show the resolved objects.
